# Копия оркестратора на VPS: грабли переезда

Читать, если поднимаешь, переносишь или чинишь сессию оркестратора проекта на сервере, либо работаешь в чекауте проекта на VPS. Выделено из AGENTS.md (#24, 03.08.2026; V-48, 17.10.2026). Первичный документ передачи: `docs/HANDOFF-to-vps.md`.

## Что было сделано и зачем
Оркестратор проекта (`kesha-tg-bot-orchestrator`, роль orchestrator) перенесён на сервер, чтобы работать с воркерами при выключенном ноутбуке. Своего systemd-сервиса и venv у оркестратора нет и не нужно: бот живёт отдельно в `/opt`. Ветки задач живут на VPS. С переезда (#24, 03.08.2026) `main` ведёт оркестратор на VPS: мерж и push идут отсюда (до переезда его вёл ноутбук); общий remote — GitHub. Прод тянет из `origin`, поэтому незапушенный `main` значит «на проде вчерашний код». Боевой каталог бота (`/opt/kesha-bot`) оркестратору не трогать.

## Грабли (все пойманы при самом переезде, 03.08.2026)
- `su - kesha` виснет (нет пароля): `su -s /bin/bash kesha`.
- Каталог проекта должен целиком принадлежать `kesha`: `find <проект> ! -user kesha | wc -l` обязан дать 0, иначе `git fetch` умрёт позже.
- **Сессию в БД Orchestra руками не создавать.** `_ensure_orchestrator` молчит, если оркестратор уже есть, а ручной INSERT неполон: `save_session()` проставляет ~20 умолчаний. Правильно: скрипт с `save_session()` + `resolve_model()` + `backend_for_model()`, запускать из каталога Orchestra её интерпретатором (иначе `No module named 'app'`; `uv` под `su` не в PATH).
- `system_prompt` в БД — оверлей поверх собранной роли, а не сама роль; скопируешь чужой — получишь двойную личность.
- Перед любым `systemctl stop orchestra` проверить `select name,status from sessions where status='running'`: остановка рвёт ходы всех агентов, включая чужие проекты.
- Тестового venv у воркеров нет: см. `rules-verification.md`.
