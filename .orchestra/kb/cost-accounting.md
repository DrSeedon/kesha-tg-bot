# Стоимость и токены ответа: что отдаёт Claude Agent SDK и как это считать

Поисковые слова: `total_cost_usd`, `model_usage`, `ResultMessage.usage`, `response_usage`,
cost per response, накопительный счётчик, цена токена opus-5, cache_creation ephemeral_1h.

Проверено 19–20.09.2026 на проде (`/opt/kesha-bot`, SDK `claude-agent-sdk` 0.2.152) и
контрольными прогонами против `claude-opus-5`. Перепроверять при смене версии SDK или модели.

## Три источника в терминальном `ResultMessage`, и только один полный

| поле | семантика | что считает |
|---|---|---|
| `AssistantMessage.usage` | снимок на СТАРТЕ сообщения | входная сторона точна, `output_tokens` — нет (6 при реальных 242) |
| `ResultMessage.usage` | за один запрос | только главного агента, без субагентов и вспомогательных моделей |
| `ResultMessage.model_usage` | НАКОПИТЕЛЬНО по сессии | всё, включая haiku и субагентов |
| `ResultMessage.total_cost_usd` | НАКОПИТЕЛЬНО по сессии | деньги за всё |

Доказательство полноты `model_usage`: сумма `costUSD` по его моделям совпадает с
`total_cost_usd` до копейки (0.270708 против 0.27070825). Разница с `usage` на том же
ответе: out 1443 против 912, cache_create 28 157 против 11 296.

Доказательство накопительности (решающий замер — второй запрос заведомо крошечный):
в одном соединении ответ на 357 токенов дал `cost=0.2174`, следующий ответ на 3 токена —
`0.2318`, следующий на 4 токена — `0.2429`. Трёхтокенный ответ «дороже» — значит это
счётчик, а не цена. `model_usage` ведёт себя так же: out 399 → 402 после ответа в 3 токена.
На SDK Orchestra 0.2.114 картина та же, то есть это не свойство одной версии.

**Отсюда правило: цена и токены ответа = ДЕЛЬТА накопителя.** Значение меньше предыдущего
означает, что счётчик перезапустился с новой сессией CLI, и тогда оно само и есть цена ответа.
Orchestra (`app/backend_claude.py`) пишет `total_cost_usd` как есть — у неё соединение
пересоздаётся на ход, поэтому инфляции в данных нет (906 пар подряд идущих ходов, рост лишь
в 44.6%). Для долгоживущего соединения, как у бота, сырое значение врёт: строки росли
5.17 → 6.26 → … → 47.94 за сессию.

Размер контекста из `ResultMessage` НЕ получить: его входная сторона — сумма по вызовам
ответа (1 459 171 при реальных 730 857 на трёхвызовном ответе). Контекст берётся из
последнего `AssistantMessage.usage`: `input + cache_read + cache_creation`.

## Цены claude-opus-5, восстановленные из данных

По четырём боевым строкам `response_usage` методом наименьших квадратов (3 неизвестных):

| | $ за 1M токенов |
|---|--:|
| output | **25.00** |
| cache read | **0.50** |
| cache create (1h) | **10.00** |

Совпадение точное, расхождение 0.0% на всех четырёх строках, включая ответ с 816 013
токенами записи кеша. Числа согласуются между собой: cache read = 10% входа, запись
часового кеша = 2× вход, то есть вход ≈ $5/1M. Это прайс, по которому SDK считает
`total_cost_usd`; с реальным списанием по подписке Max его смешивать нельзя.

Практическое следствие: проверять учёт формулой со СТАРЫМИ ценами opus-4
(75 / 1.5 / 18.75) нельзя — на ответе, где доминирует запись кеша, она даёт ложную
тревогу о «недосчёте токенов» (строка 101: мнимое отклонение +48%, фактическое 0.0%).

## Разбивка TTL

`ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` есть только в
`ResultMessage.usage.cache_creation`; в `model_usage` разбивки нет. Значит сумма записи
кеша может быть полной, а её разбивка по TTL — только по главному агенту.
На боевых данных за 30 дней 5-минутная запись кеша = 0 во всех ответах обоих чатов:
бот пишет только часовой кеш, и эксперимент «5 минут против часа» ставить не на чем.
