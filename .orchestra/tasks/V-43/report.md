# V-43 — отчёт: фоновая работа CLI ведёт себя нативно

План лежит в `plan.md`: одобрен 14.10, развилка решена в пользу A, протокол рантаймов не тронут.
Доказательства — в `research.md` и `spikes/`.

## Причина инцидента

Первоначальная посылка «CLI был занят своим ходом» не подтвердилась. CLI простаивал с 10:29:40 до
10:30:18 UTC, а обе пробы падали в 10:29:57 и 10:30:07. Бот читал поток SDK только внутри
`send_message`. Между ходами буфер SDK на 100 кадров переполнялся, его читатель вставал, и
control-канал умирал вместе с ним. Это замерено на настоящем `Query` SDK 0.2.158: при 100 кадрах
проба отвечает, при 101 — таймаут (research §1). Если поток читать постоянно, `get_context_usage`
отвечает за 0.01–0.5 с даже посреди хода (research §2, живой CLI 2.1.280).

## Что сделано

- `claude_session.py`
  - `_ClientStream`: один постоянный читатель на клиента. Кадры уходят в неограниченную очередь,
    там же ведётся учёт открытых фоновых агентов (`DEFERRING_TASK_TYPES` из SDK).
  - Промпт уходит с нашим uuid, опция `replay-user-messages` включена.
  - `_turn_chunks` размечает ходы по эху. Ход наш, только если в нём было эхо нашего uuid.
  - `background_turns()`, `has_background_turn()`, `background_agents_open()`,
    `set_background_listener()` — необязательная поверхность, как `abort_turn` в V-42.
  - `PROMPT_PICKUP_TIMEOUT_S = 60` даёт ошибку `prompt_lost`.
  - Проба при живом потоке возвращает `unmeasured` без reconnect.
  - Нативный `/compact` читает свой ход из очереди и пропускает notification-ходы.
  - `inject()` и `_expected_results` удалены.
- `chat_state.py`
  - Ходы CLI запускают фоновый рендер в IDLE. Если чат был занят, их подхватывает
    `_drain_or_idle`.
  - Компакт (admission, после хода, ручной) ждёт завершения фоновых агентов.
  - `/clear` сообщает, сколько задач остановлено.
  - Пост-ходовая проба ограничена 10 с.
- `response_stream.py`
  - Режим `prompt=None` рендерит ходы CLI без ретраев и без «Пустого ответа».
  - `turn_done.ours` отделяет ходы CLI от ответа. «Пустой ответ» показывается, только если наш ход
    ничего не показал.
  - Поток закрывается явно (`aclose`).
  - Режим дельт сбрасывается на границе хода. Обрыв без пузырей теперь сообщается.
- `handlers.py`: `/stop` называет число фоновых задач, которые остановятся вместе с ходом
  (research §5: interrupt в SDK-режиме глушит все фоновые задачи).
- Codex не изменён. `runtime_protocol.py` не тронут.

## #29 («после reconnect сессия отстаёт на ход и глотает ответы»)

**Закрыто:**
- Причина двойного таймаута пробы: недренированный буфер SDK.
- Reconnect по таймауту пробы при живом CLI.
- Счётчик `_expected_results`, из-за которого ход забирал Result предыдущего хода. Теперь Result
  засчитывается вопросу только по эху его uuid.
- Залипание «навсегда до рестарта»: каждый ход размечается независимо.
- Чужой Result больше не выдаётся за «🤷 Пустой ответ».

**Не закрыто:**
- «Fail loud, если терминал пришёл без чанков за <1 с» для **нашего** хода не сделан. Наш
  действительно пустой ход по-прежнему даёт «🤷 Пустой ответ». Громкой ошибкой стал только
  промпт, который CLI так и не взял (`prompt_lost`).
- Синтетический хвост CLI после убитого хода (`Continue from where you left off.` /
  `No response requested.`) не проверен: может всплыть в чате фоновым ходом. Записано в TODO.

## Ограничения и риски

- `/stop` при живых агентах останавливает их: это нативное поведение CLI 2.1.280, обойти его
  нечем.
- Атрибуция зависит от эха `--replay-user-messages`. При смене поведения CLI вопрос завершится
  `prompt_lost` через 60 с, но не повиснет.
- Компакт при живом фоновом shell (`local_bash` без конца) не блокируется: в учёт идут только
  агенты, по той же причине, что и в SDK.
- После рестарта бота итоги агентов прошлого процесса приходят при следующем вопросе, потому что
  подключение ленивое (TODO).
- Python-изменения требуют рестарта `kesha-bot-vps` после деплоя.
