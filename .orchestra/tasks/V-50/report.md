# V-50 — генерация изображений через хаб

Реализовано в рабочей копии. Деплой, конфигурация MCP и окружение прода не менялись.
Обязательный полный сьют **не зелёный**: в копии отсутствует исходный модуль
`scripts/evaluate_compact_prompt.py`. Остальные результаты ниже.

## Изменения

- `codex_session.py`: `tool_timeout_sec` и `startup_timeout_sec` из записи MCP
  проходят через нормализацию в приватный `config.toml`, в таблицу сервера, перед
  таблицей `env`. Принимаются положительные конечные числа в секундах; строки,
  boolean, null, ноль, отрицательные значения, NaN и infinity отклоняются без
  вывода конфигурационных значений. Для старых записей поля не добавляются.
- Codex учитывает открытые инструменты по `item.id` (запасной источник —
  `params.itemId`), передаёт `liveness` в `response_stream` и закрывает запись
  на `item/completed`. Повторные события не раздувают счётчик; чужие ходы
  игнорируются; счётчик локален одному ходу. Изменение охватывает и остальные
  уже распознаваемые инструменты, включая команды оболочки.
- `system_prompt.txt`: основной инструмент `hub_generate_image`, `count=1`;
  перед вызовом — короткое сообщение о рисунке и ожидании около минуты;
  каждый файл из `paths` обязательно отправляется через `send_photo`.
  При ошибке/отсутствии хаба — честное уведомление и одна попытка платного
  `mcp__websearch__generate_image` / `nano-banana`. Сохранены английский промпт,
  одна картинка за раз и обязательная отправка результата запасного инструмента.
  JSON-пример экранирован для реального `load_system_prompt().format(...)`.
- `file_access.py`: устранены два воспроизведённых обхода проверки хардлинков.
  `lstat()` исключает симлинк из подсчёта имён inode, множество путей исключает
  повторный подсчёт при пересекающихся корнях. Дефолтные корни не менялись.
- README в обоих языках: строка о хабе и платном запасном варианте.
  CHANGELOG: minor `v2.13.0`.

## Таймауты

Реально запущен `--version` бинарника `claude_agent_sdk/_bundled/claude` из
SDK **0.2.158**: **Claude Code 2.1.280**. Затем прочитан код этого бинарника,
а не системного CLI; повторяемая проверка — `inspect_cli.py`, вывод —
`cli-inspection.txt`.

| Ограничение | Значение и применение |
|---|---|
| Claude MCP hard timeout по умолчанию | `1e8` мс = **100000 с**, функция `nr` |
| Claude stdio MCP idle timeout по умолчанию | **1800 с**, функция `vs` |
| Claude per-server `timeout` | Миллисекунды; при значении ≥1000 имеет приоритет над `MCP_TOOL_TIMEOUT` |
| Claude `MCP_TOOL_TIMEOUT` | Миллисекунды, используется при отсутствии применимого `timeout` сервера |
| Claude `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` | Отдельная настройка idle-сторожа; стандарт stdio — 1800 с |
| Codex MCP tool timeout | На деплое задать `tool_timeout_sec: 400`; теперь сохраняется в TOML |
| Бот `CHUNK_TIMEOUT_TEXT` | **120 с**, ожидание следующего чанка без открытой работы вне tool/result-фазы |
| Бот `CHUNK_TIMEOUT_TOOL` | **300 с**, следующий чанк после tool/result, когда нет открытой работы |
| Бот `CHUNK_TIMEOUT_OPEN_WORK` | **1800 с**, имеет приоритет, пока рантайм сообщает хотя бы один открытый инструмент/задачу |

У Claude `ToolUseBlock` уже открывал запись работы без необходимости `task_started`;
`ToolResultBlock` в `UserMessage` закрывает её. У Codex этого учёта не было —
именно он попадал на 300 с, исправлено. Поэтому 370 с укладываются и в 400 с
Codex MCP, и в 1800 с сторожей. Числа в `response_stream.py` и код Claude
менять не потребовалось. У Codex 180 с для JSON-RPC `turn/start` ограничивают
ответ о начале хода; дальнейшие уведомления читаются отдельно, это не лимит
выполнения инструмента.

Для stdio-сервера Claude стандарт уже выше 400 с. Если оператор хочет явно
закрепить бюджет независимо от унаследованного окружения, в ту же MCP-запись
можно добавить `timeout: 400000` рядом с `tool_timeout_sec: 400`. Укороченный
нестандартный idle override также требует внимания оператора. В коде нет
жёстко заданного адреса сервера, секретов или каталога хаба.

## Файлы и регрессии

В тестах абсолютный внешний каталог `orchestra/data/generated-images` создан
внутри временного каталога рабочей копии: ограничения доступа не позволяют
создавать реальные каталоги вне неё. Проверяются именно прочитанные байты
`open_sendable`, а не только проверка строки пути:

- PNG читается при добавленном корне и блокируется после удаления корня из env;
- симлинк и хардлинк между разрешёнными корнями работают;
- симлинк/хардлинк наружу блокируется;
- симлинк внутри корня и пересекающиеся корни не маскируют внешний хардлинк;
- прежние TOCTOU, размер, traversal и стандартный whitelist покрыты старым набором.

Два новых теста хардлинков сначала упали на старом коде (`hardlink-regression-before.txt`).
Мутации передачи timeout и учёта открытых инструментов тоже делают соответствующие
тесты красными. `verify_regressions.py` восстановил исходник побайтно; после
восстановления **42 passed** (`mutation-summary.txt`, `regressions-restored.txt`).

Интеграционные тесты используют настоящие адаптеры Claude/Codex и `_ask_inner`
с поддельными SDK/RPC-событиями. Бюджеты масштабированы в 1000 раз: тишина
0.370 с соответствует 370 с и переживает пороги 120/300 с. Успешный вызов
доставляет итог; зависший вызов в обоих рантаймах всё ещё останавливается
на эквиваленте 1800 с с одним уведомлением. Реальный платный вызов не запускался.

## Проверки и ограничения копии

Во всех Python-прогонах использован provisioned **uv 0.11.28**, не системный
диспетчер. В копии нет `pyproject.toml`/`uv.lock`, поэтому команда `uv run --frozen`
для проектного окружения неприменима. Использована запрошенная команда с пинами
прода, в том числе для setup, inspection, smoke и целевых тестов:

```bash
export PATH="$HOME/.local/share/orchestra/tools/uv/0.11.28/bin:$PATH"
export TMPDIR="$PWD/.orchestra/tasks/V-50/tmp"
export KESHA_NO_FILE_LOG=1
export KESHA_CODEX_USER_HOME="$TMPDIR/codex-user"
uv run --isolated --no-project --exclude-newer 2030-01-01 \
  --with-requirements requirements.txt --with mcp==1.28.1 \
  --with claude-agent-sdk==0.2.158 --with pytest --with pytest-asyncio \
  python -m pytest -q tests
```

`tmp` нужно создать перед повтором. SDK/MCP-версии подтверждены в
`cli-inspection.txt`. Тесты используют поддельные данные и локальные транспорты;
live-тесты не включались. Внешние обращения за зависимостями выполнял только uv.

| Прогон | Результат / сырой вывод |
|---|---|
| Целевые: Codex, liveness, file access, reload | **154 passed, 3 skipped**, `targeted-tests.txt` |
| Реальная загрузка и форматирование промпта | **PASS**, `prompt-smoke.txt` |
| Запрошенный полный сьют | **exit 2**, сборка остановлена на отсутствующем `scripts`, `full-suite.txt` |
| Диагностика с `--continue-on-collection-errors` | **645 passed, 3 skipped, 2 failed, 1 collection error**, `available-suite.txt` |
| Два теста Unix-сокетов с короткими относительными временными путями | **2 passed**, `unix-socket-checks.txt` |
| Все доступные тесты с короткими путями и продолжением после ошибки сборки | **647 passed, 3 skipped, 1 collection error**, `available-suite-short-paths.txt` |

Для короткой диагностики ошибок использовались `--tb=short --show-capture=no`.
Оба дополнительных падения вызваны `AF_UNIX path too long`: абсолютный путь
временного файла в глубокой рабочей копии превышает лимит Unix-сокета, а писать
в обычный `/tmp` по правилам воркера нельзя. Тестовый plugin `short_unix_tmpdir.py`
меняет только временный путь этих двух тестов на относительный внутри каталога
задачи; утверждения о доставке, правах 0600 и удалении сокета остаются прежними.
Подключение plugin: добавить каталог задачи в `PYTHONPATH` и `-p short_unix_tmpdir`.

Требуется повтор полного сьюта в полной копии с `scripts/evaluate_compact_prompt.py`.
Регистрация MCP-сервера, настройка таймаутов и `KESHA_SENDABLE_ROOTS`, права на
реальный выходной каталог, живая генерация и доставка в Telegram остаются
проверками оркестратора на деплое. Замены отсутствующего исходного модуля,
сетевого вызова генерации, git-операций и деплоя воркер не делал.
