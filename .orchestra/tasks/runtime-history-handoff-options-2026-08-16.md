# Перенос истории между Claude и Codex: варианты контракта

Статус: проект решения. Двусторонний перенос в коде пока не реализован.

## Что существует сейчас

У чата три разных слоя состояния:

1. `messages.db` хранит видимые сообщения пользователя и финальные ответы Кеши. Это
   единственный нейтральный к провайдеру журнал.
2. Claude хранит собственную native session, Codex — собственный thread. Их идентификаторы
   и внутренний формат не совместимы.
3. При Claude → Codex Кеша берёт до 40 последних видимых сообщений, ограничивает их
   24 000 символов и пассивно добавляет в Codex через `thread/inject_items`. Обратного
   безопасного ingress у текущего Claude adapter нет, поэтому Codex → Claude начинается
   без handoff.

`thread/inject_items` действительно добавляет Responses API items в уже загруженный
Codex thread без запуска model turn. `thread/compact/start` сжимает только native Codex
thread; это не переносимый summary-файл. См. [Codex App Server](https://developers.openai.com/codex/app-server).

## Что нельзя перенести

Скрытое reasoning нельзя считать общей историей. Оно может не возвращаться клиенту,
может быть зашифровано/сжато провайдером и не имеет общего формата между Claude и Codex.
Переносить следует наблюдаемое состояние: сообщения, подтверждённые факты, решения,
результаты инструментов и незакрытые задачи. Нативные provider logs остаются кэшем
конкретного backend, а не источником истины.

Anthropic Messages API в обычном режиме stateless: приложение передаёт историю сообщений
на каждом запросе. Agent SDK отдельно поддерживает resume своих sessions, но этот session id
не понимает OpenAI. См. [Anthropic Messages](https://platform.claude.com/docs/en/build-with-claude/working-with-messages)
и [Agent SDK session browser](https://platform.claude.com/cookbook/claude-agent-sdk-05-building-a-session-browser).
OpenAI также разделяет ручную передачу истории и provider-owned conversation state:
[Conversation state](https://developers.openai.com/api/docs/guides/conversation-state).

## Варианты

### 1. Передавать сырой видимый transcript

Плюсы: минимум логики, почти нет смысловых потерь, легко проверить глазами.

Минусы: быстро съедает контекст; повторно тащит старый шум; роли и tool events приходится
нормализовать; старая формулировка задачи может выглядеть как новая команда. Полные native
логи сюда не годятся: в них provider-specific события, внутренние идентификаторы, stderr,
иногда секретные аргументы инструментов и огромные payload.

### 2. Source-модель сама делает summary перед уходом

Плюсы: она видит собственную native session лучше приложения.

Минусы: переключение чаще всего нужно именно потому, что source исчерпал лимит или сломался.
Получается аварийный выход, который требует последнего успешного вызова аварийного backend.
Кроме того, source оптимизирует summary под своё понимание, а читать его будет другая модель.

### 3. Target-модель получает raw delta и сама его compact'ит

Это ближе всего к идее «новая модель сама приготовит себе память». Делать это надо отдельным
stateless вызовом без tools, MCP, файлов и побочных эффектов, а не первым агентным turn в
рабочей session. Иначе старое «удали/отправь/запусти» может случайно стать действием.

Плюсы: summary написан под возможности и лексику принимающей модели; source может быть мёртв.

Минусы: дополнительная стоимость и задержка; summarizer всё равно не видит скрытое reasoning;
summary остаётся вероятностным и может потерять отрицание, число или незакрытый вопрос.

### 4. Структурированная handoff capsule приложения

Приложение собирает переносимый объект:

- подтверждённые факты с источником/`message_id`;
- принятые решения;
- выполненные действия и короткие результаты tools;
- открытые задачи и вопросы;
- последние 6–12 сообщений дословно;
- граница `/clear` и курсор последнего успешно принятого сообщения.

Капсула строится детерминированно из `messages.db`; при большом delta отдельная target-модель
может только сжать её в строгую JSON-схему. Исходные последние сообщения сохраняются рядом,
чтобы summary не был единственной копией факта.

## Рекомендация

Использовать гибрид варианта 4 и 3:

1. `messages.db` — canonical visible transcript; provider sessions — ускоряющий кэш.
2. Хранить отдельный `handoff_cursor` для каждого `(chat_id, target_runtime)` и переносить
   только delta после него и после последнего `/clear`.
3. Маленький delta передавать нормализованным сырьём. Большой — отдавать отдельному
   tool-disabled target summarizer в строгую capsule-схему.
4. В Codex вставлять capsule пассивно через `thread/inject_items`. Для Claude прикладывать
   capsule к следующему реальному сообщению пользователя как явно размеченный context block,
   а не запускать отдельный агентный turn.
5. Продвигать cursor только после подтверждённого ingress/успешного первого turn. До этого
   хранить pending handoff с idempotency key, чтобы crash не потерял и не продублировал перенос.

Это не перенос «мозга» модели — такого API нет. Это перенос проверяемого рабочего состояния,
который переживает разные провайдеры, лимиты и рестарты.
