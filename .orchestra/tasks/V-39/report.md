# V-39 — максимум шагов Claude

## Результат

`CLAUDE_MAX_TURNS = 150` задан в `config.py` и используется в `ClaudeAgentOptions`; вызов больше не содержит магическое число. Комментарий к константе фиксирует причину: циклы GPB и сходные задачи могут проходить десятки последовательных вызовов инструментов, а прежние 25 останавливали допустимую работу.

Проверка установленного `claude-agent-sdk==0.2.158` и его bundled CLI `2.1.280` показала: в stream-json result schema и в ветке формирования max-turn результата CLI использует `subtype="error_max_turns"`, `is_error=true` и текст `Reached maximum number of turns (...)` в `errors`; в этой ветке `terminal_reason` не задаётся. SDK parser переносит subtype из JSON в `ResultMessage`. `ResultError` — отдельное поведение после выхода CLI и не основной путь постоянного stream-клиента.

Основная обработка в `ClaudeSession.send_message()` распознаёт subtype (и `terminal_reason="max_turns"`, если он присутствует), не обрабатывая событие как обычную ошибку и не отключая клиента. На terminal result сессия остаётся подключённой. `response_stream.py` один раз отправляет в ту же сессию инструкцию продолжить с незавершённого шага. Второй упор завершает ответ русским сообщением с предложением написать «продолжай». Квота, context-limit и обычные ошибки автопродолжение не запускают; обработка V-38 не менялась. В `codex_session.py` проверены строки `max_turn`, `turn limit` и `max steps` — аналогичного потолка там нет, файл не менялся.

Первоначальный фикс обрабатывал только `ResultError` и потому не покрывал путь постоянного stream-клиента. После проверки ветки приёмки он исправлен: добавлена отдельная обработка max-turns именно в полученном `ResultMessage`.

## Проверки

- Целевые тесты: **74 passed**.
- Приёмочный полный suite на `mcp==1.28.1` и `claude-agent-sdk==0.2.158`: **665 passed, 3 skipped**, 35.06s (последний запуск).
- `test_stream_result_max_turns_is_reported_without_disconnect` подаёт SDK `ResultMessage` с формой stream-терминала через `receive_messages()` заглушки; проверяет kind, текст CLI, сохранённый session ID и живое соединение.
- Мутация stream-распознавания (`error_max_turns` заменён другим subtype) покраснила этот тест: он получил пустой список чанков после лога `Result: ..., stop=tool_use` — тот же молчаливый путь, что в прод-логе.
- Мутация предела автопродолжения с 1 до 2 покраснила тест, который ограничивает количество запросов и использует заглушку, бросающую на дополнительном вызове.
- Мутация условия события так, чтобы оно совпадало с обычной ошибкой/квотой, покраснила тест отсутствия автопродолжения для квоты.
