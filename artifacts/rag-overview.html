RAG-память Кеши: что построено и стоит ли это в Orchestra

Гибридная семантическая память: 5930 чанков из 1586 диалогов и 1318 файлов базы знаний, единым поиском (bge-m3 + sqlite-vec + FTS5 + RRF). Переживает compact/restart. Ниже — полная архитектура, метрики, эволюция качества — и разбор, стоит ли встраивать аналог в саму Orchestra как память агентов.

1Архитектура

Один процесс бота, отдельный поток на embed/search. Модель, sqlite-vec и FTS5 живут в выделенных потоках (SQLite thread-affinity). После оптимизации #10 — раздельные read/write потоки: поиск не ждёт индексацию.

3Качество

Две метрики решали дизайн: separation margin (выбор модели) и MRR на контрольных запросах (выбор чанкинга). Всё замерено на боевых данных, не на синтетике.

Separation margin по моделям (шире = чётче отделяет релевантное)

bge-m3 = +0.237 vs e5-large +0.063 vs e5-small +0.055 — в 4× шире. На абстрактных русских запросах («еда», «психология») bge-m3 стабильно вытаскивал топ-1.

Retrieval: heading-aware чанкинг vs naive (multi-doc, с дистракторами)

Markdown heading-aware бьёт naive char-window: top-3 5/5 vs 4/5, MRR 0.90 vs 0.70, чистый старт чанка (заголовок/список, не посреди фразы) — 100% vs 33%. При масштабе с дистракторами разница решает.

Контроль на проде: 5/5 запросов → топ-1 (включая еду, психологию, тренировки).

Ключевая оптимизация: поиск не ждёт индексацию

Было: single-thread executor → search стоял в очереди за embed-батчами backfill'а 300с → reconnect. Профиль: embed 82ms/chunk vs insert 0.6ms (138×) — узкое место CPU-embed, не SQLite. Фикс: RO/RW split + WAL (37 конкурентных читений/0 ошибок) + shared embedder (ONNX thread-safe). Результат: 37ms во время тяжёлого backfill (было ~300000ms). ~7300×.

RAM-история (честно про грабли)

e5-large int8 (561MB) → OOM на старом VPS 2.9GB. mpnet тоже OOM. Root cause: FastEmbed грузил все docs одним вызовом → onnxruntime arena раздувалась. Фикс: batch_size + enable_cpu_mem_arena=False. Переезд на Contabo 8GB снял ограничение → bge-m3 (1024d).

6Watcher, дедуп, атрибуция

watchfiles live watcher

Rust inotify, async-native awatch(), встроенный debounce. Файл создан/изменён/удалён → индекс обновляется в реальном времени, пишет через тот же executor.

sha256 дедуп

Ключ по content-hash + path. mtime сменился, контент нет → skip. Изменился → delete старых чанков + reindex. Prune удалённых с диска.

Source attribution

Результат несёт source: [file: rel/path] для заметок, [ts | role] для диалога. role фильтрует ТОЛЬКО диалоги — файлы всегда ищутся.

Chunk-level retrieval

Файловый FTS keyed by chunk_id → находит и возвращает НУЖНУЮ секцию 50-чанкового файла, а не весь файл целиком.

7RAG для Orchestra — стоит ли встраивать

Вопрос: дать агентам Orchestra такую же семантическую память — чтобы они помнили прошлые задачи, решения и ошибки через compact/restart, и искали по docs/tasks всех проектов. Разбор по фактам (проверено в репо Orchestra), не по ощущениям.

Факт (проверено в репо)

Orchestra сейчас НЕ имеет embedding/RAG (grep пусто). SQLite data/orchestra.db: sessions, logs, tm_tasks, bg_jobs. 1146 файлов docs/tasks/*.md по всем проектам — ровно то, что RAG бы индексировал как память агентов. Плюс таблица logs = история турнов.

Архитектурные развилки

Общий RAG vs per-project

Общий индекс + фильтр по project (как chat_id у Кеши). Один embedder, одна vec.db, партиция/фильтр по проекту. Кросс-проектный поиск — фича, не баг (агент видит решение из другого проекта).

Где embedder

Orchestra = долгоживущий FastAPI-процесс. Embedder-синглтон в отдельном потоке (как у Кеши после #10). +1.2GB RSS на сервер — единожды, не per-agent.

Кто индексирует

Фоновый процесс, не агент. watchfiles на docs/tasks/**/*.md + хук на запись logs. Агент только search_memory (MCP-тул). Детерминизм: агент не решает «индексировать ли».

Scaling

1146 файлов + логи ≈ 5-15K чанков. vec0 brute-force держит <100ms до ~50K. На горизонте года — хватает без ANN-индекса.

Моё мнение (строил это)

Да, стоит — но начать узко. Самая большая отдача не от индексации ВСЕХ логов (там 90% шума — tool-вызовы, статусы), а от docs/tasks/*.md: research/plan/report/retro уже дистиллированы человеком и агентом. Это готовый корпус «памяти решений» — 1146 файлов лежат и не используются семантически.

Фаза 1 (эта отдача): индексировать только docs/tasks/**/*.md + BUGS.md + CLAUDE.md-заметки. watcher + search_memory MCP-тул. Реюз rag.py ядра. ~2 дня. Агент после рестарта спрашивает «делали похожее?» → достаёт прошлый research/retro. Низкий риск, высокая польза.

Фаза 2 (если зайдёт): селективная индексация logs — не сырые турны, а извлечённые «решение/ошибка/правило» (LLM-фильтр на входе, как self-improvement RULE). Тут риск шума — делать после того как Фаза 1 докажет ценность.

Не делать: индексировать всё подряд из logs сырьём — это утопит сигнал в 90% tool-шума и раздует vec.db без пользы. И не делать per-project изоляцию — кросс-проектная память («в polus решали похожий SQL-баг») это киллер-фича, а не утечка.

Вердикт: MEDIUM, делать Фазу 1, ядро rag.py переносится 1:1
