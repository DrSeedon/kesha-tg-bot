2Чанкинг: heading-aware vs naive

Гипотеза (до замера): markdown heading-aware чанкинг ищет лучше naive char-window, потому что чанки семантически цельные (одна секция = одна тема, чистые границы). Метрики зафиксированы ДО прогона: top-1/top-3 hit rate + MRR на контрольных запросах через реальный bge-m3.

Проблема naive-чанкинга — фрагмент посреди фразы

✗ NAIVE (char-window 800)
...охлаждает — испарение (80%) + сдувание тёплой "шубы" (20%). В бане — обратный эффект. Тепловой насос — КПД 300-500%, перекачивает...
✓ MD-AWARE (heading section)
### Термодинамика и энергия - Почему вентилятор охлаждает — испарение (80%)... - Тепловой насос — КПД 300-500%, перекачивает тепло...

Naive начинает чанк с «...охлаждает — испарение» — без темы, эмбеддится плохо. Md-aware несёт хлебную крошку заголовка (Physics > Термодинамика) → изолированный факт получает контекст.

Вывод: CONFIRMED

md-aware чанкинг для .md: делим по заголовкам #..######, несём хлебную крошку; секция >1500 симв → делим по параграфам; секция <250 симв → мержим с соседней; файл без заголовков (дневники) → параграфы. .txt → параграфы. Fallback → старый char-window.

Как читать «single-doc naive выиграл» — не двигал goalposts

Метрики зафиксированы ДО прогона. Single-doc результат (naive 5/5) записан как есть — это p-hacking-safe. Но single-doc с ~10 чанками нерепрезентативен: без конкурентов любой чанк близко к топу. Реальный корпус = 2600+ чанков с дистракторами, где фрагмент посреди фразы конкурирует плохо. Multi-doc замер это подтвердил (MRR 0.90 vs 0.70). Оба замера в research.md.

3inotify: watchfiles vs watchdog

Требование — живой watcher (не cron, не при старте). Ловить create/modify/delete в реальном времени. Ресёрч 4 вариантов под asyncio-интеграцию бота.

ВариантasyncioDebounceBackendВердикт
watchfiles native async for … in awatch() встроен Rust notify (inotify) ВЫБРАН
watchdog thread-based нужен мост hachiko/custom DIY (threading.Timer) inotify лишний клей
pyinotify нет руками inotify (Linux-only) unmaintained
inotifywait subprocess парсинг stdout нет inotify CLI хрупко

Почему watchfiles

awatch() — async-генератор множеств {(Change, path)}. Никакого моста thread↔loop, никакого threading.Timer.

Встроенный debounce схлопывает пачку «редактор сохранил 5×» в один reindex.

Change = added/modified/deleted → index/reindex/delete напрямую.

Прод-факты (замерено)

fs.inotify.max_user_watches = 61659, корпус = 100 директорий → бюджет не проблема.

Все sqlite-записи идут через rag_executor (single-thread) — watcher enqueue'ит, thread-affinity соблюдён.

4Схема БД (v7 → v8)

Главный вызов: существующая схема — message-centric (chunk_id = msg_id*1000+idx, chat_id PARTITION KEY, content джойнится из messages.db). Файлам это не подходит. Решение — отдельные файловые таблицы, диалоговый путь не трогаем.

Namespaced RRF — почему не схлопнутся id-пространства

Диалоговый msg_id и файловый chunk_id — оба маленькие int, могут совпасть. Если фьюзить по голому int, message #5 и chunk #5 слились бы в RRF. Fix — namespaced ключи:

# диалог → ("d", parent_message_id) · файл → ("f", chunk_id)
# chunk-level (НЕ дедуп до file_id!) → matched секция и есть результат
d_vec = [("d", m) for m in self._vec_search(chat_id, qvec, pool, role)]
f_vec = [("f", c) for c in self._vec_search_files(qvec, pool)]
ranked = self._rrf(d_vec, d_fts, f_vec, f_fts)   # union, ключи не коллизят

Миграция безопасна

Bump v7→v8 дропает только производные индекс-таблицы и ребилдит: диалоги из messages.db (проверенный backfill), файлы с диска (backfill_files). messages.db никогда не трогается. Это установленный паттерн (v6→v7 делал то же при смене модели).

5Дедупликация: sha256 + delete-reindex

Изменился файл → удалить старые чанки → переиндексировать. НЕ дублировать. Ключ дедупа — sha256 контента, по path. mtime — дешёвый пре-фильтр.

Поток index_file

файл→ chunk_file()→ sha256(content)→ files WHERE path=?
sha совпал→ no-op (0) | sha изменился→ delete старые чанки→ re-embed + insert→ UPDATE files
Событие watcherДействие
addedindex_file — новый file_id, чанки, sha
modifiedsha совпал → skip; иначе delete старых + reindex
deleteddelete_file — все чанки path из vec/fts/file_chunks/files

Почему sha256, а не только mtime

mtime меняется на любой touch (git checkout, rsync, сохранение без правок). Хэш контента = источник правды «изменился ли смысл». mtime = дешёвый пре-фильтр (не изменился → не хэшируем).

Prune stale (по подсказке Codex): backfill_files удаляет из files записи, чьих путей больше нет на диске — консистентность после удалений пока watcher был выключен.

6Source attribution

Результат search_memory должен показывать откуда факт — из файла или диалога. Каждый результат несёт source-дискриминатор.

Из файла
[file: 01-daily/2026-06-08-daily-dump.md] ### Термодинамика Тепловой насос — КПД 300-500%...
Из диалога
[2026-06-08T14:30 | user] напомни какой кпд у теплового насоса

role-фильтр применяется только к диалогам — у файлов нет роли, при заданном role файлы исключаются. Path хранится относительным от WORK_DIR (/opt/cog-second-brain), рендерится инструментом.

7Codex review

Cross-LLM ревью (GPT-5.5) на план И на имплементацию. Оба раза поймал реальное.

План · BLOCKING

File FTS/RRF был file-level. Запрос по одной секции 50-чанкового файла вернул бы ВЕСЬ файл. Fix: FTS keyed by chunk_id, RRF фьюзит ("f",chunk_id) — matched секция, не файл. Внесено в план ДО имплементации.

Impl · "blocking" (оспорено)

Codex: «DELETE FROM fts_files WHERE chunk_id=? по UNINDEXED-колонке может не работать». Я эмпирически опроверг (в sqlite работает — тест удалил строку). Но применил идиоматичный rowid=chunk_id → O(1) delete, ноль сомнений.
